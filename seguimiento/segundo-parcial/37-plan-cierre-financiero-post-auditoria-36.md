# Plan de corrección financiera y cierre E2 tras auditoría 36

**Fuente:** [auditoría independiente 36](36-auditoria-independiente-post-checkpoint-35.md). **Estado:** E2 en avance sin aceptar. **Contrato:** 0.3.2, protocolo 0.4.0. **Encargo ejecutable:** [prompt para el agente y tres subagentes](prompts/E2-correccion-financiera-auditoria-36-subagentes.md). Se conservan Stripe Elements de las dos cajas, stock libre CU19, cupos exclusivos CU06/CU07, CU05, CU22 y push ya mejorados. El agente entrega sin commit para revisión posterior.

## Decisiones de implementación que deben quedar demostradas

1. **Compromiso de inventario compartido.** Al iniciar CU19 Stripe, bloquear filas de inventario en orden determinista y mover cada unidad desde `disponible` hacia una cantidad comprometida persistente, ligada a la venta/orden. Efectivo, saldo, catálogo y cualquier otra ruta que consume stock deben ver inmediatamente el nuevo `disponible`. Los cupos CU06/CU07 permanecen en `comprometido_caja`; no sirven como reserva Stripe. Registrar Kardex de compromiso/liberación si el modelo de movimientos lo exige. Al liquidar un PI capturado, consumir el compromiso de esa misma venta una vez sin volver a descontar `disponible`. Al cancelar un PI verificado, liberar exactamente su compromiso una vez. No usar un conteo de `PENDIENTE_PAGO` como única reserva.
2. **Stripe fuera de locks SQL.** No esperar a `gateway.crear_o_reutilizar_intencion`, `consultar_intencion` o `cancelar_intencion` mientras se retienen locks de inventario/venta. Separar transacciones de reserva, operación proveedor y conciliación final. La clave idempotente y el recurso persistente deben permitir recuperar un PI creado aunque falle el commit posterior, sin duplicar venta, cargo ni Kardex.
3. **Cancelación honesta.** Un error, timeout o rechazo al cancelar en Stripe conserva la orden y venta como pendiente/incierta y el compromiso de stock hasta consultar el estado real. Si el PI fue capturado, se confirma/conciliará y se liquida o reembolsa conforme CU27. Sólo la cancelación externa verificada permite `CANCELADO` y liberar stock. Webhook y petición de usuario concurrentes producen una sola transición final. No usar `except Exception: pass` para convertir incertidumbre en éxito.
4. **Vida y recuperación.** Asignar `expira_en` o equivalente a la venta Stripe pendiente según decisión documentada. Al expirar, consultar PI antes de liberar stock; vencimiento por sí solo no prueba que no hubo cobro. Crear o adaptar consulta autenticada para recuperar órdenes propias pendientes/capturadas por tenant, sucursal, cajero o turno; devolver el `client_secret` sólo por una ruta autorizada que lo recupere de Stripe cuando sea necesario. La PWA conserva como mucho IDs opacos y recupera estado central tras recarga, logout/relogin y error de red; no guarda tarjetas ni `client_secret` localmente.
5. **Pertenencia estricta.** Para las órdenes CU19 nuevas, metadata de empresa y venta ausente o incongruente impide `CAPTURADO`. Si existen PI heredados sin metadata, tratarlos mediante una ruta de compatibilidad explícita, limitada y probada; no debilitar la verificación general.

## Criterio para recomendar cierre

Ningún camino puede captar fondos y perder la venta, liberarla como cancelada sin respuesta del proveedor o entregar una prenda comprometida por otro medio. La suite incluye los contraejemplos entre medios, fallo de cancelación externa, captura concurrente con cancelación, vencimiento y recuperación; no bastan dos `iniciar_stripe` concurrentes ni mocks que devuelven `CAPTURADO` desde el principio. La verificación independiente posterior decide aceptación y commits. Si falta configuración para proveedores reales o Android físico, el checkpoint declara esa prueba externa pendiente con causa concreta y conserva la distinción entre código, dobles y servicio externo.
